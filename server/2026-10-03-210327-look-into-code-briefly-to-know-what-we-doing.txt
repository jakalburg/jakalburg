    wrappers around it. faq.tsx and about.tsx have their own shapes.
  - Every page keeps its original hardcoded copy as a fallback, used when the
    API is down or an admin flips the page inactive — so a route never renders
    empty.

● Both errors were real bugs. Fixed and verified against live Cloudinary.

  1. favicon.ico rejected

  UploadService's MIME whitelist had no .ico entry — the endpoint was built for
  product photos, and favicons never came up. Added image/x-icon and
  image/vnd.microsoft.icon, plus an extension fallback (.heic|.heif|.ico)
  because curl and some OSes send application/octet-stream for .ico instead of a
  real type.

  2. mini_logo.png — Cloudinary "Request Timeout"

  Two causes, both fixed:

  - No timeout was ever configured. cloudinary.config() had no timeout, so it
    used the SDK default. Set to 120s at config and per-upload — an admin is sat
    waiting, so waiting beats failing.
  - Three uploads fired at once. My handleSave ran logo, mini logo and favicon
    through Promise.all, so they contended on the same link. Now sequential.
    That's what made a 307KB file time out when the same file uploads fine
    alone.

  Also added a retry on timeout (3 attempts) in CloudinaryService. Only timeouts
  retry — bad credentials or a rejected format fail immediately rather than
  wasting your time three times over.

  Better failure behaviour

  The old toast said "Failed to upload the brand marks" with no clue which one.
  Now it names the mark and the reason: "Nothing was saved — an image failed to 
  upload / Favicon: Unsupported image type…". Nothing is written when an upload
  fails, so your form still holds everything and you can just retry.
