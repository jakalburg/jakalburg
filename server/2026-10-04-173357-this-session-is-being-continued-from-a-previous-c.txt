● /settings/notifications is real now. Here's what was there and what changed.

  What I found

  Same trap as before, plus a worse one underneath it: every hook was on
  useAxiosAuth() (mockAxios), the userId came from @/lib/mock-auth, and the 
  server had no notifications module at all. The six toggles saved to nothing
  and the header bell was rendering invented rows.

  Server (new src/notifications/)

  Two Prisma models in prisma/models/Notification.prisma, plus a module with
  five guarded routes:

  GET   /api/notifications            PATCH /api/notifications/read-all
  PATCH /api/notifications/:id/read
  GET   /api/settings/notifications   PATCH /api/settings/notifications

  All @AdminOnly() — verified mapped and returning 401 unauthenticated. There's
  no create route; rows are only written by the server when an order event
  actually happens.

  Wired into OrdersService: create() raises the bell alert and gates the owner
  email; adminUpdateStatus(), adminShip() and adminReject() raise alerts on real
  transitions only (re-shipping an already-shipped order doesn't ring twice).

  Two judgment calls worth flagging

  The preferences are a store-wide singleton, not per-user. The admin UI and kay
  both keyed them by userId, but that userId was the mock session value — it
  identifies nobody. And the toggles aren't personal preferences: they decide
  how the shop behaves, and the owner-email recipient comes from Settings →
  Email, not from a user account. So the endpoint has no id segment.

  I rewrote the toggle copy rather than copying it. Kay's three email switches
  all read "Receive an email when…", but only the first one mails you — the
  other two mail the customer. As written, the shipped toggle claimed to email
  the owner when the owner themselves marks an order shipped. The labels now
  name the recipient. Related: the customer's order-placed confirmation is
  deliberately not gated by any toggle — it's the receipt for a purchase, not a
  notification — and adminUpdateStatus now returns emailBlockedByPreference so a
  ticked "Notify customer" box that sent nothing can say why.

  On the free tier: the bell polls at 60s instead of kay's 30s, and read
  notifications are pruned after 30 days from findAll at most once an hour — no
  cron, nothing runs on an idle store. Unread rows are never pruned.

  GET /api/notifications now takes status, type, search, from, to on top of the
  standard pagination params, and returns the normal envelope. Three design
  calls:

  unreadTotal rides along on the list response. The badge needs it on every
  render, and folding one more COUNT into a connection that's already open beats
  a second HTTP round trip to a free-tier database. It deliberately ignores the
  active filters — it means "how much is outstanding overall", so it shouldn't
  move as you narrow the table.

  The response shape changed from a bare array to the pagination envelope. The
  header bell reads the same endpoint, so I updated it to unwrap via
  toPaginated, which also tolerates a bare array — an older API build won't
  blank the bell.

  Added @@index([type, createdAt]) to match the new filter against the sort
  column.

  Two lint rules caught real problems

  react-hooks/purity flagged Date.now() during render for the period window.
  Rather than suppress it, the component now passes withinDays (a span) and the
  hook resolves it to a timestamp inside queryFn — which also fixes a genuine
  bug: a tab left open overnight was asking for the 7 days before it loaded, not
  the real last 7 days.

  react-hooks/set-state-in-effect flagged resetting the page number in an
